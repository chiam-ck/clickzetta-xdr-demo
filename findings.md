# Synthetic xDR evaluation findings

These observations came from synthetic data in a temporary ClickZetta test environment. Tenant identifiers, user identities, job/request IDs, local infrastructure details, screenshots, and raw result files have been intentionally omitted. No severity ratings are assigned.

## BSS customer tagging — September 2026

The separate [BSS measured report](bss_tagging/MEASURED_REPORT.md) contains
sanitized aggregate measurements, not raw account telemetry or billing rates.
All 26 remote correctness snapshots and 10 local tests passed.

| Area | Finding | Minimal fix or operational response |
|---|---|---|
| Small-delta maintenance | At 1M customers and 1.5M subscriptions, five repeated 100-customer deltas used median 3.070 CPU seconds versus 4.798 for full rebuild, and wrote 50,104 bytes versus 2,120,355. Changed stages reported INCREMENTAL; unaffected stages reported NO_DATA. | Report both actual resource counters and refresh modes, not the incremental label alone. |
| Fixed overhead and billing | The five-refresh chain took 5.571 server seconds versus 1.476 for full rebuild. The 80% active-compute reduction target was not met; lower all-in billing was not demonstrated. | Separate CPU work from elapsed time and cluster billing; include idle capacity and ingestion. Account-specific prices are withheld from this public copy. |
| Fixed-delta scale | Growing the customer base from 100k to 1M with the same 100-customer delta increased incremental CPU only 3.6% and logical inputs 2.1%. | Scope the result to these tested sizes and warm-cluster conditions; do not extrapolate an invoice reduction. |
| Catalog fanout | One offering-family change affected 80k customers. Subscription features remained incremental, but joined customer features and tags refreshed FULL. | Estimate affected-customer fanout; one changed dimension row need not be a small workload. |
| Unchanged cycles | Five no-change cycles at 100k used median 0.004 CPU seconds and zero profile input/output bytes; all five dynamic tables reported NO_DATA. | An awakened cluster may still incur activation and idle costs. |
| Correctness | Payments, complaint closure, ageing, termination, consent updates and deletion matched full recomputation. Deleting 100 customers left exactly 99,900 customer/tag rows. | Verify retractions, bidirectional equality, uniqueness and cardinality after each scenario. |
| EXPLAIN REFRESH | A join plan probe failed with CZLH-66000 and optimizer message `should not have join operator here`, while actual refresh succeeded. | Preserve the failed probe privately, capture defining-SELECT EXPLAINs, and use successful refresh history for actual incrementality. |
| Metadata syntax | CURRENT_ROLE was not recognized; SHOW JOBS filtering on virtual_cluster could not resolve that column. | Use CURRENT_ROLES() and SHOW JOBS IN VCLUSTER <cluster>. |
| Metering availability | Current-day job history and experiment compute billing were not yet available when direct profiles and SHOW JOBS already exposed executions. | Keep invoice totals unknown until posted; do not treat profile CPU units as independently billed job charges. |
| Profile counters | A 100-row audience query reported 101 internal output rows and negative inputDiskBytes. | Use the actual SQL result row count; do not derive physical I/O or egress charges from these counters. |

## xDR evaluation

| Area | Finding | Minimal fix or operational response |
|---|---|---|
| Storage connection DDL | `CREATE STORAGE CONNECTION ... TYPE S3 ... REGION = '...'` failed with `CZLH-65000 Compiler internal error - missing mandatory config keys - ENDPOINT`. DDL submission was asynchronous, so the initial response showed `RUNNING`; the error only appeared when polling the job result. | Add `ENDPOINT = 's3.<region>.amazonaws.com'` and poll every asynchronous DDL job before running dependent statements. |
| Refresh history syntax | `SHOW DYNAMIC TABLE REFRESH HISTORY schema.table` failed with `CZLH-42000 Syntax error`. An `EXPLAIN SELECT` against an already-materialized dynamic table did not establish whether its defining query could be incrementalized. | Use `SHOW DYNAMIC TABLE REFRESH HISTORY WHERE NAME='<table>'` and use the history's `refresh_mode` for the empirical incremental/full result. |
| COPY INTO replay behavior | Re-running `COPY INTO ... FROM VOLUME` appended the same files again. `load_history()` provided an audit record but did not prevent replay. | Treat the landing prefix as a consume-once queue with `PURGE=TRUE`, or implement explicit file selection/checkpointing. |
| COPY INTO purge permissions | A `PURGE=TRUE` load completed successfully even though the storage identity lacked `s3:DeleteObject`; source files remained and were appended again on the next schedule. | Grant narrowly scoped `s3:DeleteObject` and verify that the landing prefix is empty after every successful load. Alert if loaded objects remain. |
| Initial dynamic-table refresh | Initial population refreshed incrementally; idle cycles reported `NO_DATA`. A truncate/reload upstream caused a downstream full refresh. | Avoid truncate/reload in the normal ingestion path and monitor `refresh_mode`, rows inserted, and rows deleted. |
| Retractions | A clean correction batch of 200 re-rated IDs caused the dedupe dynamic table to delete 200 superseded rows and insert 8,200 rows, while downstream revenue matched a fresh recomputation. An earlier apparent full rewrite was traced to a duplicate 48,000-row append in the same cycle rather than to the correction itself. | Keep `record_version`-based deduplication, prevent landing-file replay, and validate correction cycles independently from bulk repairs. |
| Steady-state cost | With append-only 8,000-row batches, the session table inserted roughly the delta and the hourly rollup updated only affected groups. Most one-minute refresh cycles were `NO_DATA`. | Choose refresh intervals from freshness needs; do not assume no-data refreshes are free without checking account billing metrics. |
| Very-late arrivals | More-than-24-hour-late rows updated old event hours incrementally rather than forcing a full refresh. | Continue tracking refresh history across late-arrival distributions representative of the intended workload. |
| Reliability flag grain | A default threshold of 50 very-late records never marked any recent cell-hour provisional because the threshold had been conceived at hour grain but applied at cell-hour grain. | Set the default to 1 for the current cell-hour grain, or explicitly aggregate and calibrate the rule at hour grain. |
| Exact versus approximate distinct | At low cell-hour cardinalities, `APPROX_COUNT_DISTINCT(msisdn)` matched exact distinct counts in the test and did not change refresh behavior. | Benchmark both at production-like cardinality before claiming a cost or accuracy advantage. |
| Studio task API authorization | Creating a task in a folder failed with `IDE-USER_NO_PERMISSION / CZSD_ADMIN_USER_NO_PERMISSION_ERROR`, while creating the folder succeeded. The API identity therefore had partial Studio permissions. | Verify Studio IDE scopes separately from Lakehouse SQL rights; test task creation without a folder or request the missing Studio permission. |
| Grant syntax | `GRANT SELECT ON SCHEMA ...` failed because `SELECT` is table-level, and `GRANT USAGE ON VCLUSTER ...` failed because the accepted action was `USE`. | Use `GRANT SELECT, READ METADATA ON ALL TABLES IN SCHEMA ...` and `GRANT USE ON VCLUSTER ...`. Verify syntax against the current product documentation. |
| Dynamic-table and masking grants | Table grants did not cover dynamic tables. A reader of a masked column also needed permission to use the masking function; without it, the query failed instead of returning a masked value. | Grant the dynamic-table class explicitly and pair masking rollout with `USE FUNCTION` for every intended reader. |
| Grant propagation | Newly granted permissions took several minutes to become effective, returning the same no-permission error during propagation as a genuinely missing grant. | Automate a bounded verification poll after access changes and record propagation latency. |
| Agent identity | A separate read-only identity could read tables/dynamic tables, saw subscriber identifiers masked, and was denied `DELETE`. | Preserve a distinct agent identity, least-privilege roles, masking-function rights, and a negative write test. |
| Scheduler and auto-suspend | A one-minute dynamic-table cadence kept the compute cluster active, so auto-suspend did not materially engage during the observation window. | Lengthen refresh intervals or suspend dynamic tables outside demonstration/operating hours, then validate the actual billing effect. |
| CLI compatibility | One native CLI release raised `SIGILL` on a virtual CPU without the instruction extensions it expected. An older Python-packaged release worked in the same environment. Published installer asset names also differed from the referenced release assets during the test. | Use a compatible packaged release or expose host CPU features to the VM; pin and verify installer URLs before automation. |
| MCP availability | No separately installable ClickZetta MCP server was found during the evaluation; the available MCP component was bundled with a newer CLI build that did not run on the test CPU. | Use the CLI-backed read-only harness until a supported MCP distribution is available for the target platform. |
